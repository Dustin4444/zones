# Earn Zone benchmark — 2026-07-22

## Target and boundary

- Zone: `tempo-zone-unstable`, revision `4a7ad33a890b3a9bfe891cc15596529f987f0ade`
- Tempo L1: revision `0e067a50bbb7a4e463129ac36824162834e46a6b`
- Earn: revision `4fd9b5e997546d5435ee5f922e1e8ee2821bdb3d`
- Input/output asset: `AlphaUSD`, the current live DLUSD analogue
- Venue: `Tempo Earn Local Vault`, a zero-fee `Simple4626` fixture
- Boundary: direct viem request submission through the terminal L1 or private-Zone RPC read

This is protocol E2E. There is no Privy-like API in the Earn repository, so these measurements do
not include HTTP routing, Privy networking, signing-service, or HSM latency.

## Serial latency

Ten consecutive $10-equivalent AlphaUSD journeys completed successfully on the live devnet.

| Use case         | Terminal condition                                                                            |      p50 |      p95 |
| ---------------- | --------------------------------------------------------------------------------------------- | -------: | -------: |
| Payout           | L1 encrypted deposit submitted, then private Zone balance readable                            |  0.730 s |  1.157 s |
| Earn             | Zone request submitted, vault callback settled, private EarnToken readable                    |  4.407 s |  6.450 s |
| Redeem           | Zone request submitted, vault redemption and AlphaUSD swap settled, private AlphaUSD readable |  3.022 s |  4.696 s |
| Offramp          | Zone request submitted, L1 withdrawal processed, public AlphaUSD balance readable             |  2.721 s |  4.601 s |
| Complete journey | Payout through final public balance read                                                      | 13.222 s | 16.768 s |

The ten-run result used one allowlisted account serially. It is a latency baseline, not a concurrency
or 1,000-distinct-user result.

## Complete cost accounting

The cost table below joins the user transaction, the L1 batch submission, the full
`processWithdrawals` transaction, and the returned encrypted-deposit batch where applicable. Zone
receipts used gas but had an effective gas price of zero.

Three adjacent use cases shared each active batch submission in the audited journey. To avoid
double-counting, each 61-micro-pathUSD batch charge is divided across the external Zone transaction
and L1 deposits it commits.

| Use case              | Cost composition                                                          | Actual system cost |
| --------------------- | ------------------------------------------------------------------------- | -----------------: |
| Payout                | 58µ user L1 transaction + ⅓ × 61µ batch                                   |   **$0.000078333** |
| Earn                  | ⅓ × 61µ outbound batch + 295µ `processWithdrawals` + ½ × 61µ return batch |   **$0.000345833** |
| Redeem                | ½ × 61µ outbound batch + 278µ `processWithdrawals` + ½ × 61µ return batch |   **$0.000339000** |
| Offramp               | ½ × 61µ outbound batch + 55µ warm `processWithdrawals`                    |   **$0.000085500** |
| Four-use-case journey | No shared batch counted twice                                             |   **$0.000848667** |

The separate private PATHUSD setup deposit cost 50µ and owned the remaining one-third of its shared
batch. Including that setup, but excluding periodic empty-batch fleet overhead, the audited canary
spent **$0.000919**.

For standalone pricing, where each operation is isolated and charged every batch it needs, the
costs are payout $0.000119, Earn $0.000417, redeem $0.000400, and warm offramp $0.000116. Do not sum
those figures for the combined immediate journey because they intentionally charge shared batches
more than once.

### Gas and non-amortizable processing

| Use case                       |    Zone gas p50 / p95 | `processWithdrawals` L1 gas p50 / p95 | Actual L1 process charge |
| ------------------------------ | --------------------: | ------------------------------------: | -----------------------: |
| Earn, AlphaUSD swap in         | 5,846,165 / 5,846,165 |                     491,087 / 491,097 |                $0.000295 |
| Redeem, swap back to AlphaUSD  | 6,096,165 / 6,096,177 |                     462,119 / 462,141 |                $0.000278 |
| Offramp, warm public recipient | 1,793,879 / 1,793,879 |                       90,293 / 90,293 |                $0.000055 |

All 617 historical Portal calls inspected on this live deployment contained exactly one withdrawal,
and the sequencer currently calls `processWithdrawals` with a one-element array. That cost is not
amortizable today. A first receipt into a cold public token account was separately observed at
339,077 gas, or $0.000204, so a 1,000-new-user offramp cohort should use the cold figure unless the
destination accounts are already warm.

Current `submitBatch` calls contain empty verifier configuration and empty proof bytes. The measured
61µ is a signed batch-submission/attestation cost, not a production validity-proof cost.

## 1,000-user cost envelope

A real 1,000-user run must sum its own receipts and divide each batch by the actual user-caused inputs
or withdrawals in that batch. Before that run, the measured non-amortizable lower layer is:

| Component for 1,000 users                       | Warm offramp destinations | Cold offramp destinations |
| ----------------------------------------------- | ------------------------: | ------------------------: |
| 1,000 payout L1 transactions                    |                    $0.058 |                    $0.058 |
| 1,000 Earn `processWithdrawals` transactions    |                    $0.295 |                    $0.295 |
| 1,000 redeem `processWithdrawals` transactions  |                    $0.278 |                    $0.278 |
| 1,000 offramp `processWithdrawals` transactions |                    $0.055 |                    $0.204 |
| Subtotal before batch submissions               |                **$0.686** |                **$0.835** |

As a deliberately conservative ceiling, six dedicated 61µ batch submissions per user add $0.366
for the cohort, producing **$1.052 warm** or **$1.201 cold** for all 1,000 users. Actual shared-batch
cost should be lower and cannot be known until the concurrent run is executed.

## 1,000-distinct-user readiness

The referenced GitHub Actions result used 100 leased accounts for 1,000 repeated journeys on an
isolated local topology. It was not 1,000 distinct users and did not target this live devnet.

The live hourly Earn deployment authorizes only its single scenario account in the protected TIP-403
recipient policy. A genuine 1,000-user run therefore needs a reviewed, benchmark-specific deployment
that pre-authorizes all users and waits for Zone policy mirroring. The required local credentials are
not present:

- `EARN_ACCESS_ADMIN_PRIVATE_KEY`
- `DEPLOYER_PRIVATE_KEY`

Do not fetch these through 1Password implicitly. The safer execution path is a reviewed one-off Argo
workflow that consumes the existing cluster secret by reference, runs 10-user and 100-user gates,
then starts the 1,000-user cohort while the hourly liveness workflow is paused or mutexed.
